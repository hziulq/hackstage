# Feature Specification: apiの自動テスト整備

**Feature Branch**: `005-api-tests`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "003-user-authで実装済みの認証機能(登録・ログイン・ログアウト・自分の情報取得・ログイン試行のレート制限)と、認証実装の副作用として認証必須化されたtodos CRUDについて、自動テストを整備する。現状apps/apiにはtests/ディレクトリが存在せず、検証はquickstart.mdの手動curlシナリオのみに依存している。この機能では、quickstart.mdの各シナリオを自動テストとしてコード化し、CIや今後の変更のたびに手動でcurlを叩かなくても回帰を検知できる状態にする。認証のようなセキュリティ影響の大きい機能が無テストで積み上がっているリスクを解消することが目的。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 開発者として認証機能の回帰を自動で検知する (Priority: P1)

開発者(自分または将来のメンバー)が、認証関連のコード(`apps/api/app/auth/`, `app/routes/auth.py`, `app/models/user.py`)を変更した際、手動でcurlを叩かなくても、登録・ログイン・ログアウト・`/api/me`・レート制限の挙動が壊れていないかを機械的に確認できる。

**Why this priority**: 認証はセキュリティ影響が最も大きい機能であり、`003-user-auth`で実装済みだが自動テストが一件も無い。手動確認(`quickstart.md`)は実施者の手間に依存し、変更のたびに漏れなく行われる保証がない。

**Independent Test**: `apps/api/tests/`配下の認証テストのみを実行し、登録成功・重複登録拒否・ログイン成功・ログイン失敗時の一律エラー・ログアウト後の未ログイン状態への遷移がすべてパスすることを確認すれば、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** テスト用データベースが空である、**When** 認証テストスイートを実行する、**Then** 新規登録・重複登録拒否・ログイン成功・ログイン失敗時の一律エラー・ログアウトと未ログイン状態への遷移の各シナリオがすべて自動で検証される。
2. **Given** 認証コードに意図的な不具合(例: パスワード照合を常にtrueにする)を混入させる、**When** テストスイートを実行する、**Then** 該当するテストが失敗し、不具合が検知される。

---

### User Story 2 - 開発者としてtodosの所有者分離の回帰を自動で検知する (Priority: P2)

開発者が、`app/routes/todos.py`を変更した際、未ログイン時の拒否と、ログイン中の利用者が自分のTodoのみを操作できること(他人のTodoが見えない・操作できない)が壊れていないかを機械的に確認できる。

**Why this priority**: `003-user-auth`のPolishフェーズで`todos.py`の暫定実装(`user_id`クエリパラメータ)を`current_user.id`に置き換えたが、この所有者分離を保証する自動テストが無い。将来の変更で退行(他人のデータが見える等)するリスクがある。

**Independent Test**: `apps/api/tests/`配下のtodosテストのみを実行し、未ログイン時の401、ログイン中の利用者による自分のTodoのCRUD、他人のTodoへの非到達がすべてパスすることを確認すれば、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 未ログイン状態である、**When** `/api/todos`にアクセスする、**Then** 拒否されることが自動で検証される。
2. **Given** 2人の利用者がそれぞれ自分のTodoを持っている、**When** 利用者Aとしてログインし一覧・詳細取得を行う、**Then** 利用者Bのtodoが一切含まれない・到達できないことが自動で検証される。

---

### User Story 3 - 開発者としてレート制限の回帰を自動で検知する (Priority: P3)

開発者が、ログインエンドポイントのレート制限設定を変更・削除してしまった場合に、自動テストで検知できる。

**Why this priority**: ブルートフォース対策の要であり、他のUser Storyより実装コストは低いが、うっかり削除・緩和されたことに気づけないと総当たり攻撃への耐性が失われる。

**Independent Test**: `apps/api/tests/`配下のレート制限テストのみを実行し、規定回数以内は失敗しても401、超過後は429になることを確認すれば、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** レート制限の閾値が設定されている、**When** 同一送信元から閾値を超えてログインを試みる、**Then** 超過分が429になることが自動で検証される。

---

### Edge Cases

- テスト実行が本番/開発用データベース(`db`サービス)を汚染しない状態になっているか?(テスト用に分離されたDB、または各テスト後のロールバックが必要)
- レート制限はインメモリストレージ(`memory://`)のため、テスト実行順序やテスト間の状態共有によって意図せず制限に達し、他のテストが誤って失敗しないか?
- 同一メールアドレスを使う複数テストが並行実行された場合に、重複登録エラーと衝突しないか?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: テストスイートは、`quickstart.md`シナリオ1(登録→ログイン→自分の情報取得→ログアウト→ログアウト後の`/api/me`)を自動テストとして実行できなければならない。
- **FR-002**: テストスイートは、`quickstart.md`シナリオ2(重複登録の拒否)を自動テストとして実行できなければならない。
- **FR-003**: テストスイートは、`quickstart.md`シナリオ3(ログイン失敗時の一律エラー。存在しないメールアドレスと誤ったパスワードで同一の応答になること)を自動テストとして実行できなければならない。
- **FR-004**: テストスイートは、`quickstart.md`シナリオ4(レート制限。規定回数超過後の429)を自動テストとして実行できなければならない。
- **FR-005**: テストスイートは、`quickstart.md`シナリオ5(`/api/todos`の認証必須化)を自動テストとして実行できなければならない。
- **FR-006**: テストスイートは、複数利用者間でのtodosの所有者分離(他人のtodoが見えない・操作できない)を自動テストとして実行できなければならない。
- **FR-007**: テストの実行は、開発用DB(`db`サービス、`compose.yaml`で定義)上のデータを汚染してはならない。テスト前後でデータが残留しない状態にしなければならない。
- **FR-008**: テストスイートは、devcontainer内(`dev`コンテナ)から実行できなければならない(憲章 原則VI)。
- **FR-009**: テストスイート全体の実行は、開発者が1コマンドで起動できなければならない。

### Key Entities

- **テストスイート**: `apps/api/tests/`配下に置く。認証(登録/ログイン/ログアウト/me/レート制限)とtodos(認証必須化/所有者分離)の観点でファイルを分ける。
- **テストデータ**: テスト実行のたびに作成される利用者・todoのレコード。既存の開発用データと混在しないよう分離・後始末される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `quickstart.md`に記載された全5シナリオが、手動でのcurl実行なしに自動テストとして再現・検証できる。
- **SC-002**: 認証・認可に関わるコードへ既知の不具合(例: 他人のtodoが見える、パスワード照合が常に成功する)を混入させた場合、対応するテストが失敗し不具合を検知する。
- **SC-003**: テストスイートを連続して2回実行しても、1回目の実行で作成されたデータが原因で2回目が失敗しない(再実行可能)。
- **SC-004**: 開発者は1コマンドでテストスイート全体を実行し、結果(成功/失敗件数)を確認できる。

## Assumptions

- テストフレームワークやDB分離方法などの技術的な実現手段は本specの対象外とし、`/speckit-plan`で決定する。
- 型生成(`openapi.json`生成)やCIワークフロー自体の整備は本featureの対象外とする(それぞれ別feature `006-openapi-generation` / `007-ci-setup` で対応)。
- フロントエンド(`apps/web`)の自動テストは本featureの対象外とする(api側のみ)。
- 既存の`quickstart.md`は本featureの完了後も残す(手動での最終確認手段として)。自動テストへの一本化(quickstart.md撤廃)は行わない。
