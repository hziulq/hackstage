# Feature Specification: ユーザー認証(ログイン・ログアウト)

**Feature Branch**: `003-user-auth`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "Flask-Loginを使ったユーザー認証機能。メール+パスワードでのログイン/ログアウト/現在のユーザー取得(/api/me)。パスワードはargon2でハッシュ化。ログイン試行にレート制限。未決事項: ユーザー登録(サインアップ)の方法、メールアドレス確認の要否、パスワードリセットの要否、匿名掲示板の運用とアカウントの関係、退会・アカウント削除の要否。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新しい利用者としてアカウントを作る (Priority: P1)

就活中の学生が、メールアドレス・パスワード・表示名を入力して、誰でも自由にアカウントを作成できる(オープン登録)。

**Why this priority**: ログインの前提として、そもそもアカウントが作れなければ利用が始まらない。招待制ではなく、誰でも自由に始められることを優先する。

**Independent Test**: 未登録のメールアドレスで登録APIを呼び、以降そのメールアドレスとパスワードでログインできることを確認すれば、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 未登録のメールアドレスである、**When** メールアドレス・パスワード・表示名を送信する、**Then** アカウントが作成され、以降そのメールアドレスとパスワードでログインできる。
2. **Given** 既に登録済みのメールアドレスである、**When** 同じメールアドレスで登録しようとする、**Then** 登録は拒否され、既に使われている旨がわかる(メールアドレスが存在するかどうかを過度に詳しく明かさない範囲で)。

---

### User Story 2 - 登録済みユーザーとしてログインする (Priority: P1)

就活中の学生が、メールアドレスとパスワードを入力して自分専用のカレンダー・Todo・目標に到達する。

**Why this priority**: ログインできなければ、他の全機能(カレンダー共有・いいね・目標設定・掲示板)が使えない。最も基盤となる機能。

**Independent Test**: 登録済みのメールアドレスとパスワードでログインAPIを呼び、以降のリクエストで自分自身の情報が取得できることを確認すれば、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** メールアドレスとパスワードが登録済みである、**When** 正しい組み合わせでログインする、**Then** 以降のアクセスで再入力なしに本人として識別される。
2. **Given** ログイン済みである、**When** 自分自身の情報を取得する、**Then** メールアドレスと表示名が返る。
3. **Given** 登録されていないメールアドレス、または誤ったパスワードでログインを試みる、**When** ログインを実行する、**Then** どちらの原因であるかを区別できない一律のエラーになる。

---

### User Story 3 - ログアウトして識別状態を終了する (Priority: P2)

共有PCや他人の目に触れる環境でも、利用者が自分の意思で識別状態を終了できる。

**Why this priority**: 就活生の個人情報(応募状況・内定状況)を扱うため、意図的にセッションを終了できることは信頼性に直結する。

**Independent Test**: ログイン後にログアウトAPIを呼び、以降のリクエストで未ログイン状態として扱われることを確認すれば、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** ログイン済みである、**When** ログアウトする、**Then** 以降は未ログイン状態として扱われ、保護された情報にアクセスできない。

---

### User Story 4 - 不正なログイン試行から保護される (Priority: P3)

悪意ある第三者が他人のメールアドレスに対してパスワードを繰り返し試す(総当たり)行為を受けにくくする。

**Why this priority**: 直接の利用価値ではないが、就活生の個人情報(選考状況・内定状況)を守るために必要な安全性要件。

**Independent Test**: 同じメールアドレスに対して短時間に連続してログインを試み、一定回数を超えると試行が制限されることを確認すれば、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 短時間に同一の送信元から繰り返しログインが試みられている、**When** 一定回数を超える、**Then** それ以上の試行が一時的に制限される。

---

### Edge Cases

- 既に使われているメールアドレスで登録しようとした場合、どう扱うか?
- 存在しないメールアドレスでログインを試みた場合、登録済みメールアドレスに誤ったパスワードを入力した場合と同じ結果・同じ文言になるか?
- 既にログイン済みの状態で再度ログインAPIを呼んだ場合、どう扱うか?
- 未ログイン状態で、ログインが必要な情報にアクセスした場合、何が返るか?
- ログアウト済みの状態で再度ログアウトAPIを呼んだ場合、エラーにならないか?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、新しい利用者がメールアドレス・パスワード・表示名を用いて自由にアカウントを作成できるようにしなければならない(オープン登録。招待コードや所属メールアドレスによる制限は設けない)。
- **FR-002**: システムは、既に登録されているメールアドレスでの重複登録を拒否しなければならない。
- **FR-003**: システムは、登録済みのメールアドレスとパスワードの組み合わせで利用者を認証できなければならない。
- **FR-004**: システムは、認証に成功した利用者を、再入力なしに一定期間(7日間)識別し続けられなければならない。
- **FR-005**: 利用者は、いつでも明示的にログアウトし、識別状態を終了できなければならない。
- **FR-006**: ログイン済みの利用者は、自分自身の基本情報(メールアドレス・表示名)を取得できなければならない。
- **FR-007**: システムは、未ログイン状態での、ログインを要する情報へのアクセスを拒否しなければならない。
- **FR-008**: システムは、ログイン失敗時に「メールアドレスが存在しない」場合と「パスワードが誤っている」場合を、利用者から見て区別できないようにしなければならない。
- **FR-009**: システムは、短時間に繰り返されるログイン試行を制限しなければならない。
- **FR-010**: システムは、パスワードを復号可能な形式や、それに類する脆弱な方式では保存してはならない。
- **FR-011**: システムは、登録時にメールアドレスの所有確認(確認メールの送信・クリック等)を行わない。登録した時点でそのまま利用できる。

### Key Entities

- **利用者(User)**: メールアドレス・パスワード(安全な形式で保存)・表示名を持つ。カレンダーの予定・Todo・目標・掲示板投稿など、就活カレンダーアプリの各データの所有者となる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 登録済み利用者は、メールアドレスとパスワードの入力から3秒以内に自分専用の情報へ到達できる。
- **SC-005**: 新規利用者は、メールアドレス・パスワード・表示名の入力だけでアカウント作成からログインまでを完了できる(招待や承認待ちが発生しない)。
- **SC-002**: 未ログインの利用者が、ログインを要する情報にアクセスしようとした場合、100%拒否される。
- **SC-003**: ログイン失敗時のエラー表示から、そのメールアドレスが登録済みかどうかを利用者が判別できない。
- **SC-004**: 同一の送信元からの連続ログイン試行が、短時間のうちに一定回数を超えた場合、自動的に制限される。

## Assumptions

- パスワードを忘れた場合の再設定機能は本機能の対象外とする(まずはログイン・ログアウト・登録自体を完成させることを優先し、将来別機能として仕様化する)。
- ソーシャルログイン(Google等の外部IdP)は本機能の対象外とする(必要になった時点で別途検討)。
- 匿名掲示板の運用(投稿の通報・アカウント停止等)は掲示板機能側の課題とし、本機能の対象外とする。
- 退会・アカウント削除は本機能の対象外とする(将来必要になった時点で別途仕様化する)。
- ブラウザ経由の利用のみを想定し、モバイルアプリ等の外部クライアントは対象外とする。
