# nextstage Constitution

本憲章は**判断基準**を定める。レビューで変更を止める根拠はここにしかない。
具体的な設計値と作業手順は別文書にあり、本憲章はそれらを重複して持たない。

## 文書構成

| 文書 | 内容 | 読むタイミング |
|---|---|---|
| **本憲章**（`.specify/memory/constitution.md`） | 原則・禁止事項・レビューゲート | 参加時に一度、レビュー時 |
| **`docs/design.md`** | 技術スタック・構成・環境変数・API 契約・Render 設定値 | 実装中に引く |
| **`CONTRIBUTING.md`** | ブランチ運用・PR 手順・マージ衝突の解消・Spec Kit の使い方 | 作業を始める前 |

## Core Principles

### I. 規約は 1 箇所にのみ書く（NON-NEGOTIABLE）

同じ規約を 2 つの文書に書かない。1 トピックの記述場所は上表で一意に決まる。

- 原則・禁止事項の変更は**本憲章**を先に更新する MUST。
- 設計値（構成・キー名・パラメータ）の変更は **`docs/design.md`** を先に更新する MUST。
- 作業手順の変更は **`CONTRIBUTING.md`** を先に更新する MUST。
- いずれも文書を更新してから実装を変更する MUST。文書と実装が食い違った状態でのマージは禁止。
- **上記 3 文書と内容が重複する設計文書を新規に作ることは禁止。** 参照が必要なら文書名でリンクする。
- 「未決事項」の項目は既定方針のまま進める MUST。独断で別方針を実装しない。

理由: 3 担当が並行着手できるのは境界が先に固定されているからであり、参照先が重複すると
必ず片方が古くなる。旧 `ARCHITECTURE.md` を廃止したのはこの理由による。

### II. 単一公開オリジン

ブラウザから到達できるオリジンは `web` のみである。

- `api` は Private Service として運用し、インターネットへ公開しない MUST。
- ブラウザ上で動くコードから `api` を絶対 URL で呼ぶことは禁止（ホスト名・`NEXT_PUBLIC_*` 経由を含む）。
  Client Component からの `fetch` 自体は禁止しない。相対パス `/api/...` を使う MUST。
- DB へ接続するのは `api` のみ。`web` から DB へ直接接続することは禁止。
- 同一オリジンで完結するため、CORS 設定および `credentials: 'include'` の導入は禁止。
  必要になったと感じた時点で、それは経路設計の誤りである。
- `web` 側に `/api/` 配下のエンドポイントを実装することは禁止（プロキシ経路を塞ぐ）。

理由: 攻撃面を `web` 1 つに限定し、Cookie を `SameSite=Lax` のまま安全に運用できる。

### III. セキュリティ境界は api に一つだけ（NON-NEGOTIABLE）

認証・認可の判定は `api` が行う。`web` 側の制御は UX であり防御ではない。

- すべての保護エンドポイントは `api` 側で認証・認可を判定する MUST。
- 認可は所有者確認を**クエリ条件に含める** MUST（例: `filter_by(id=..., user_id=current_user.id)`）。
  取得後に `if obj.user_id != current_user.id` で弾く実装は禁止（書き忘れが構造的に起きる）。
- 権限が無い場合は `404` を返す MUST。`403` は禁止（リソースの存在を漏らす）。
- 判定できない場合は**拒否をデフォルト**とする MUST。権限は必要最小限のみ付与する MUST。
- `web` 側のガードはセッション Cookie の存在確認までとする MUST。署名検証は行わない
  （`SECRET_KEY` を持たないため検証主体になれない）。
- ログイン失敗時のメッセージは、成功・失敗の別以外を漏らさない一律の文言とする MUST。
- ログイン試行にレート制限をかける MUST。

**許容するトレードオフ**: 偽の Cookie を持つ利用者は保護ページの「枠」までは到達できる。
データ取得は `api` が 401 で拒否するため、空の画面が表示されるだけで情報は漏れない。これは受け入れる。

理由: 判定箇所が 2 つ以上あると必ず片方が漏れる。

### IV. 秘密情報をクライアントへ出さない

- セッション / トークンは **HttpOnly Cookie** で扱う MUST（属性値は `docs/design.md`）。
- `localStorage` / `sessionStorage` へのトークン保存は禁止。`document.cookie` を読む実装も禁止。
- Cookie・トークンに機密情報（パスワード、個人情報）を含めることは禁止。
- 秘密鍵・API キー・パスワードを `web` 側に置くことは禁止。`NEXT_PUBLIC_*` に機密を入れることは禁止。
- 秘密値をリポジトリや `render.yaml` に書くことは禁止。
- ログにトークン・Cookie・パスワードを出力することは禁止（Render のログは閲覧可能）。
- パスワードのハッシュは argon2 または bcrypt を使う MUST。SHA / MD5 は禁止。
- JWT は採用しない。将来移行する場合は RS256 / EdDSA を使い、秘密鍵は `api` のみが保持する MUST。
  HS256 は禁止。

理由: 一度クライアントやログに出た秘密は回収できない。

### V. 契約駆動の境界

担当間のインターフェースは生成物で共有し、手書きで二重管理しない。

- `api` は `openapi.json` を生成してリポジトリにコミットする MUST。
- `web` は `openapi.json` から TypeScript 型を生成する MUST。API 型の手書きは禁止。
- `openapi.json` は生成物である。コンフリクト時は手動マージ禁止、再生成で解決する MUST。
- 入力値の検証は `api` 側で必ず行う MUST。`web` 側の検証は UX 目的に限る。
- SQL は ORM / プレースホルダ経由とする MUST。文字列連結でクエリを組むことは禁止。
- 依存ライブラリのバージョンを固定する MUST（lockfile をコミット）。

理由: 言語が異なる 2 アプリの間で唯一同期可能なのは生成された契約である。

### VI. 開発環境は devcontainer に固定

ローカル開発は `.devcontainer/` 経由で起動したコンテナ内で行う。ホスト環境に依存しない。

- 開発作業（依存インストール、テスト、型生成、マイグレーション）は devcontainer 内で実行する MUST。
  ホスト直接の `npm install` / `pip install` は禁止。
- devcontainer は `compose.yaml` を参照する MUST。`.devcontainer/` 内に compose 定義を
  複製することは禁止（二重管理になる）。
- devcontainer のコンテナは compose ネットワーク内に置く MUST。
  ローカルでも本番と同じサービス名でアドレス解決でき、原則 II の前提が保たれる。
- 言語・ツールのバージョンは devcontainer 定義で固定する MUST。
  README に「各自インストール」と書くことは禁止。
- devcontainer 定義の変更は全員の環境を変えるため、**専用 PR** で行う MUST。
- 動作確認は devcontainer 内で行う MUST。「自分のホストでは動く」は根拠として認めない。

理由: 3 担当が別々のホスト環境を持つと「自分の環境では動く」が発生し、
境界の議論が環境差分の議論に化ける。

### VII. スケールを壊さない

- セッションはサーバー側に状態を持たない署名付き Cookie 方式である。
  プロセスメモリ上にセッションを保持する実装は水平スケールを壊すため禁止。
- 本番で待ち受けるポートは環境変数から取る MUST。固定ポートでの待ち受けは禁止。

## セキュリティチェックリスト

レビューで**全項目を照合する MUST**。未照合のままマージすることは禁止。
各項目の根拠は括弧内の原則にある。

- [ ] 権限が確認できない場合は拒否がデフォルト（III）
- [ ] 権限は必要最小限のみ（III）
- [ ] 所有者確認がクエリ条件に入っている（III）
- [ ] 権限なしは 404、403 を使っていない（III）
- [ ] 入力値を `api` 側で検証している（V）
- [ ] SQL が ORM / プレースホルダ経由（V）
- [ ] ログイン試行にレート制限（III）
- [ ] セッションは HttpOnly Cookie、localStorage を使っていない（IV）
- [ ] Cookie・トークンに機密情報を含めていない（IV）
- [ ] `NEXT_PUBLIC_*` に機密が入っていない（IV）
- [ ] 秘密値がリポジトリ・`render.yaml` に入っていない（IV）
- [ ] ログにトークン・Cookie・パスワードを出していない（IV）
- [ ] クライアントコードに `api` の絶対 URL が無い（II）
- [ ] 依存のバージョンが固定されている（V）

## 未決事項

必要になった時点で判断する。決まるまで実装担当は既定方針で進める MUST。

| 項目 | 既定方針 | 再検討の契機 |
|---|---|---|
| ソーシャルログイン（Google 等） | 実装しない | 要件化した場合 → 外部 IdP（Clerk / Auth0）を検討 |
| JWT 化 | 採用しない | モバイル・外部クライアントが必要になった場合 |
| セッションの即時失効 | 未対応 | 強制ログアウト要件が出た場合 → Redis / DB セッションストア |
| Render のプラン | 未定 | 負荷が判明した時点 |
| 型生成の自動化 | 手動実行 | CI 整備時 |
| feature 番号の採番方式 | 連番 + 事前宣言 | 番号衝突が頻発した場合 → タイムスタンプ採番 |
| CI（Lint / テスト / 型生成の検証） | 未整備 | 手動レビューが追いつかなくなった時点 |

## Governance

本憲章はプロジェクト内の他の慣習に優先する。`docs/design.md` と `CONTRIBUTING.md` は
本憲章に従属し、矛盾する場合は本憲章を正として従属文書を修正する。

**仕様記述の方針（SDD は任意）**

- Spec Kit（`/speckit-*`）の利用は**任意**とする。spec の有無を PR の受け入れ条件にしない。
- レビューは**本憲章への適合とセキュリティチェックリストのみ**で判定する MUST。
  「spec が無い」ことを理由に PR を却下することは禁止。
- 仕様を文書化する場合、`specs/NNN-slug/` 配下に置く MUST（手書きでも Spec Kit 生成でもよい）。
- したがって `specs/` は全機能を網羅しない。網羅性を前提とした運用を組まない MUST。

**改正手続き**

1. 変更内容と理由、既存実装への影響（移行が必要か）を提案に明記する。
2. リポジトリのオーナーが承認する。
3. 本ファイルを更新し、バージョンと `Last Amended` を同一コミットで更新する。
4. 破壊的変更（MAJOR）の場合は移行方針を提案に含める。
5. 憲章の変更は**専用 PR** で行う。機能実装の PR に混ぜることは禁止。

**バージョニング方針**（セマンティックバージョニング）

- MAJOR: 原則の削除・後方非互換な再定義、統治手続きの変更。
- MINOR: 原則・節の追加、または指針の実質的な拡張。
- PATCH: 文言の明確化・誤字修正など、意味を変えない改善。

**遵守レビュー**

- すべての PR で本憲章への適合を確認する MUST。
- 原則に反する実装を入れる場合は、対象箇所・理由・解消条件を PR に記録する MUST。
  記録の無い違反は却下する。
- 複雑さの追加は正当化を要する。正当化できないものは採用しない（YAGNI）。
